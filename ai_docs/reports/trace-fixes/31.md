# Review: delivery, supervision and respawn

## Result

I found 1 Critical and 8 Important defects. Five Important findings are the distinct
post-commit wake losses required by decision R10. I found no transaction that performs
mail delivery while holding its SQLite transaction, and I found no credential or unsafe
file-permission issue in the reviewed paths.

The review used run-branch revision `bfacdecb` and the landed changes from tickets 05,
14, 15, 16, 17, and 24. Ticket 42 had not landed when the review started, so it is not
part of this report.

## Critical

### C-01: A crash before orchestrator launch permanently consumes the respawn

The watchdog commits the old orchestrator handoff, inserts a new `working` orchestrator,
updates the run pointer and respawn count, and writes the wake in
`crates/horch-core/src/taskledger/orchestrator.rs:349`. It calls the external launcher only
after that transaction returns in `crates/horch/src/cmd/taskledger_watch.rs:226`. If the
watchdog exits between the commit and the call at
`crates/horch/src/cmd/taskledger_watch.rs:235`, the new worker has no PID and no lock
holder. Every later pass returns without action at
`crates/horch-core/src/taskledger/orchestrator.rs:270` and
`crates/horch-core/src/taskledger/orchestrator.rs:276`. A transient launch failure has the
same terminal result after `launch_failed` ends the new row.

Reproduction: start an active run with a registered orchestrator PID, terminate that PID,
and run one watchdog pass. Stop the watchdog after `orchestrator::check` commits but before
the launch callback starts. Restart the watchdog and run repeated passes. The run points to
a `working` orchestrator with `agent_pid = NULL`, no process starts, and the remaining
respawn budget is never used.

Impact: an active run can stop silently after one crash or one transient launcher error.
This violates C7 and TRF-38 even when 2 respawns remain.

Correction: persist a launch-pending state and make each watchdog pass reconcile it. Mark
the replacement live only after observing the lock holder. Keep launch failures eligible
for the remaining respawn budget and the 10-minute guard.

## Important

### I-01: A crash during outbox drain creates duplicate durable mail

`crates/horch-core/src/taskledger/outbox.rs:263` sends an outbox row before marking it
delivered at `crates/horch-core/src/taskledger/outbox.rs:266`. The sender durably enqueues
mail at `crates/horch/src/cmd/taskledger_wake.rs:137`. Each enqueue creates a new mail id at
`crates/horch-core/src/messaging/mail.rs:149`, so replaying one outbox row does not preserve
the C2 identity. The outbox lock prevents concurrent drains, but it cannot make this crash
window atomic.

Reproduction: create one undelivered outbox row and start a drain. Stop the process after
`tell_as` publishes its pending mail file but before `mark_delivered` runs. Start another
drain. The mailbox contains 2 pending files with different ids and the same instruction.

Impact: the orchestrator can acknowledge and execute the same actionable wake twice.

Correction: derive an idempotency key or stable mail id from the outbox row id. A retry
must find or reuse the first durable message before it marks the row delivered.

### I-02: A losing orchestrator overwrites the live orchestrator's mailbox route

`pane_launch` registers the role at `crates/horch/src/cmd/recipes.rs:997` and acquires the
single-orchestrator lock afterward at `crates/horch/src/cmd/recipes.rs:999`. Registration
unconditionally replaces `orchestrator.id` at
`crates/horch-core/src/messaging/mailbox.rs:257`. A second launch can therefore publish its
pane id and then fail the lock while the first orchestrator remains live.

Reproduction: start 2 fleet `pane-launch` processes for role `orchestrator` in the same
workspace. Let process A register and acquire the lock. Let process B register before it
fails lock acquisition. Read `orchestrator.id` or run `horch tell orchestrator`; it targets
B's non-running pane instead of A.

Impact: the lock still permits only one agent, but durable wakes and direct tells route
away from that agent. The live holder can also fail mailbox ownership checks.

Correction: acquire the workspace orchestrator lock before role registration. If that
ordering is not possible, update and restore the role mapping only while the lock is held.

### I-03: The `settled` wake is lost after task completion commits

`finish::complete` commits at `crates/horch/src/cmd/taskledger.rs:2571`, but
`wake_after_done` runs later at `crates/horch/src/cmd/taskledger.rs:2580`. A retry sets the
local `woken` guard from `c.already` at `crates/horch/src/cmd/taskledger.rs:2575` and skips
the wake. The 30-second pass only runs `after_watch` and startable reconciliation at
`crates/horch/src/cmd/taskledger_watch.rs:159`; it never re-evaluates the settled condition
implemented at `crates/horch/src/cmd/taskledger_wake.rs:182`.

Reproduction: complete the final task and stop `horch done` after the completion
transaction returns but before `wake_after_done`. Retry `horch done`, restart the watchdog,
and wait for several passes. No `settled` outbox row appears.

Impact: the orchestrator receives no instruction to verify and close a fully settled run.

Correction: write the settled row in the completion transaction, or add a settled-state
reconciler with the same board-state deduplication.

### I-04: The final `reviews-in` notice is lost after the review commits

The last review commits through `finish::complete` at
`crates/horch/src/cmd/taskledger.rs:2571`. The worker notice and fallback outbox row are
created only later by `tell_reviews_in` at `crates/horch/src/cmd/taskledger.rs:2657` and
`crates/horch/src/cmd/taskledger.rs:2691`. The fallback runs only after a failed tell; a
process crash before the tell creates neither durable role mail nor a `reviews-in` row.
The `c.already` guard prevents a retry, and the watchdog does not reconcile completed
review groups.

Reproduction: finish the last review of a parent task and stop the process after the
completion transaction but before `tell_reviews_in`. Retry `horch done` and run repeated
watchdog passes. The author receives no finish notice and no `reviews-in` outbox row exists.

Impact: the author can remain waiting for reviews that are already complete, so the parent
never advances through its finish steps.

Correction: store the `reviews-in` wake in the review-completion transaction. Deliver the
author notice from that durable row, or reconcile completed groups whose author still
waits for finish.

### I-05: The `cancelled` dependent wake is lost after cancellation commits

Cancellation commits in `crates/horch/src/cmd/taskledger.rs:936`. Dependent discovery and
the `cancelled` outbox write happen afterward at
`crates/horch/src/cmd/taskledger.rs:943` and
`crates/horch/src/cmd/taskledger_wake.rs:217`. The watchdog's generic stuck check emits
nothing while any worker is live at `crates/horch/src/cmd/taskledger_wake.rs:281`, and it
does not reconstruct the cancelled event.

Reproduction: create a blocker with queued dependents and keep an unrelated worker live.
Cancel the blocker, then stop the command after `cancel_task` commits but before
`wake_dependents`. Run repeated watchdog passes. The dependents stay blocked and no
`cancelled` row tells the orchestrator to unblock, cancel, or requeue them.

Impact: dependents can wait indefinitely with no actionable notice.

Correction: compute and write the cancelled wake in the cancellation transaction, or make
the watchdog reconcile cancelled blockers with open dependents.

### I-06: The `held` wake for an unlanded blocker is lost after completion commits

An unlanded completion commits at `crates/horch/src/cmd/taskledger.rs:2571`. Its dependent
lookup and `held` row occur later at `crates/horch/src/cmd/taskledger.rs:2660` and
`crates/horch/src/cmd/taskledger.rs:2716`. A retry skips all wakes through `c.already`.
Startable reconciliation cannot see these blocked tasks, and the generic stuck wake is
suppressed by any unrelated live worker.

Reproduction: park a task with `horch done --unlanded` while another live worker exists and
at least one task depends on it. Stop the process after completion commits but before
`wake_unlanded`. Retry done and run repeated watchdog passes. No `held` row tells the
orchestrator to requeue the parked task.

Impact: parked work and its dependents can remain blocked without the required recovery
instruction.

Correction: write the held-dependent wake in the unlanded completion transaction, or
reconcile parked blockers with open dependents on each watchdog pass.

### I-07: The held-attempt question is lost after reap commits

Manual reap commits before `after_reap` at `crates/horch/src/cmd/taskledger.rs:1435` and
`crates/horch/src/cmd/taskledger.rs:1445`. Watchdog reap has the same split at
`crates/horch/src/cmd/taskledger_watch.rs:290` and
`crates/horch/src/cmd/taskledger_watch.rs:300`. When the attempt limit holds the task, only
`after_reap` creates its operator question at
`crates/horch/src/cmd/taskledger_wake.rs:472`. The held task is not startable, so ticket
15's startable reconciler cannot recover this event.

Reproduction: reap a worker on the attempt that moves its task to held. Keep an unrelated
worker live and stop the reaper after the reap transaction but before `after_reap`. Run
repeated watchdog passes. No `held` question asks the operator to requeue, change, or
cancel the task.

Impact: a task that requires an operator decision can remain held indefinitely without a
question.

Correction: create the held question in the reap transaction, or reconcile held tasks
whose attempt-limit question has no matching outbox row.

### I-08: Reviewer auto-spawn can claim a different task than the reported review

`spawn_reviewers` loops over specific review ids at
`crates/horch/src/cmd/taskledger_spawn.rs:358`, but `CliSpawn` launches only
`horch spawn <persona> --run <slug>` at
`crates/horch/src/cmd/taskledger_spawn.rs:295`. The claim path selects the first startable
task for that persona by priority and sequence at
`crates/horch-core/src/taskledger/tasks.rs:975`. The NOTE nevertheless states that the
worker was spawned for the review at `crates/horch/src/cmd/taskledger_spawn.rs:370`.

Reproduction: queue an older startable non-review task for `codex-reviewer`, then queue one
`codex-reviewer` code-sweep review. Run reviewer auto-spawn and let the new worker claim.
The worker claims the older task, while the NOTE says it was spawned for the review and the
review remains queued.

Impact: TRF-24 can report successful reviewer coverage that did not occur. Finish remains
waiting until later reconciliation causes another worker to be spawned.

Correction: bind each auto-spawn to its review task through a claim target or reservation,
or report only the task that the spawned worker actually claims.

## Recovered crash windows

The review did not classify every post-commit window as a defect. Startable work after a
normal completion, add, unblock, requeue, or non-held reap is recovered by
`startable_rewake` in `crates/horch-core/src/taskledger/watchdog.rs:840` after the 2-minute
threshold. The unclaimed-spawn flag and wake share one transaction through
`flag_unclaimed` at `crates/horch-core/src/taskledger/watchdog.rs:969`. The current no-task,
handoff, and orchestrator-respawned paths write their outbox rows in the ledger-changing
transaction.
