# Spec: ui-prop-tester

## Problem Statement

User interfaces for browsers and terminals fail in ways that fixed end-to-end scripts rarely catch. A scripted test follows one predetermined path, whereas real defects often appear only after an unexpected sequence of interactions: rapid back-and-forward navigation across cached and non-HTML pages, clicks inside shadow roots or same-origin iframes, concurrent WebSocket or server-sent events arriving between frames, dialog prompts interrupting page script execution, sustained DOM node or listener growth over many transitions, or terminal resize events and malformed UTF-8 byte streams in a pseudo-terminal application.

When a developer or QA engineer does trigger a failure during exploratory testing, turning that failure into a fast, repeatable regression check is slow and error-prone. Long random interaction sequences are hard to replay when DOM coordinates shift slightly, and manually trimming a hundred-step trace down to the three or four actions that actually cause the violation takes significant effort.

Within the fleet, teammates responsible for frontend implementation and quality assurance need a deterministic, property-based UI exploration tool that works on both web applications and terminal applications, paired with a self-contained skill that teaches agents how to define temporal invariants and state-aware action generators, run single walks or multi-run fuzz campaigns, inspect recorded traces, replay failures, and automatically shrink counterexample traces to a minimal reproduction sequence.

## Solution

Provide `ui-prop-tester`, a clean-room Rust command-line executable in this Cargo workspace, wrapped in an own-text bundled skill `ui-prop-tester` offered to `qa-engineer` and `frontend-developer` under `available_skills`.

`ui-prop-tester` explores a target user interface in a closed feedback loop:

1. **Observe**: Capture the current UI state after activity settles. For a browser target, the tool drives Chromium over its debugging protocol, waiting for animation-frame boundaries, network/navigation events, dialogs, downloads, or synchronous exceptions, and records the URL, title, MIME type, viewport screenshot, navigation history, warning and error console entries, uncaught exceptions and unhandled promise rejections, resource counters, and JavaScript branch coverage changes. For a terminal target, the tool runs a child program inside a pseudo-terminal, feeds its output stream through a terminal emulator until output is quiet for the quiescence window (capped by a maximum drain interval for continuously repainting programs), and records the visible cell grid with full styling attributes, rendered row text, cursor state, scrollback state, child exit status or signal, and preceding action.
2. **Extract and Evaluate**: Run pure state extractors against the captured state to populate read-only state cells, then evaluate every exported temporal and state property (`now`, `always`, `next`, `eventually`, real-time `.within` bounds, and logical `and`, `or`, `not`, `implies`) over the trace so far. Built-in default properties catch common failures out of the box (HTTP status 400 or above, uncaught synchronous exceptions, unhandled promise rejections, error-level console calls, and optional sliding-window browser resource leaks; nonzero normal exit codes and Unicode replacement characters in terminal grids).
3. **Generate and Act**: Evaluate every exported action generator against the current state to build a combined weighted tree of valid candidate actions, draw a leaf and its concrete parameters from a deterministic pseudo-random generator, and dispatch the action to the browser or pseudo-terminal.
4. **Record, Inspect, Replay, and Shrink**: Write every run to a self-contained binary trace file. Users and agents can inspect traces in the terminal (`ui-prop-tester trace`) or in a local web timeline viewer (`ui-prop-tester browser inspect`), replay a recorded action sequence (`--reproduce`), and automatically minimize a failing trace (`shrink`) using calibration and confirmation runs to find the shortest sequence that still violates the target property.

The accompanying `ui-prop-tester` skill provides a deterministic launcher script, workflow instructions, property and generator authoring patterns, and trace triage guidance so fleet teammates can run property-based checks on web and terminal UIs without external setup.

## Implementation Decisions

- **Workspace Crate and Standalone Executable**: Implement the tool as a standalone Rust crate in the Cargo workspace that compiles to the `ui-prop-tester` binary. Keep it independent of `horch-core` and `horch` so that `horch`'s strict runtime dependency allowlist remains untouched and `horch`'s binary size does not grow.
- **No Code Comments and Clean-Room Provenance**: Follow the operator's repository-wide rule for this feature: write zero code comments in the new Rust crate, launcher script, or JavaScript runtime shims, and include no licence text, notice files, or upstream credit anywhere in the crate, skill, or documentation.
- **Command-Line Interface and Exit Code Normalization**:
  - Top-level subcommands: `browser` (`test`, `test-external`, `fuzz`, `shrink`, `inspect`), `terminal` (`test`, `fuzz`, `shrink`), and `trace`, plus `--help` and `--version`.
  - Exit status contract: `0` for normal completion (reaching `--time-limit`, clean interrupt handling, or `--reproduce` completing with no violation); `1` for invalid arguments, setup/driver errors, stalled browser or hung terminal target, no available actions in a state, failed reproduction divergence, or failed shrinking; `2` when one or more property violations are observed. Normalize `terminal test` to exit with status `2` on property violations (matching `browser test` and the general manual contract, rather than reproducing the researched revision's status `1` quirk) and honor `--exit-on-violation` in both `test` and `fuzz` modes.
  - Protect output paths across all commands: require the parent directory of `--output-path` to exist, refuse to overwrite an existing file unless `--output-path-overwrite` is set, and in `shrink` refuse an `--output-path` that resolves to the input `--trace` file directly, via symlink, or via hard link (checked by device and inode metadata).
- **Specification Runtime and Property Engine**:
  - Specifications are ES modules written in JavaScript or TypeScript (with lightweight type-annotation stripping before evaluation).
  - Top-level exports are classified by runtime tag into properties (temporal formulas) and action generators. The export identifier names the property in violation reports and `--property <NAME>`.
  - State extractors execute against the current captured state and cache their JSON-serializable result in a cell for that state index. Attempting to read another extractor's cell while extraction is currently running throws a clear runtime error. Uncaught exceptions in an extractor abort the run with status `1` and format the JavaScript stack trace.
  - Temporal formula AST and stepper:
    - `now` evaluates its predicate callback in the current state; bare callbacks passed to temporal or logical operators are promoted to `now` automatically.
    - `always` steps its subformula at the current state and spawns a continuing obligation for every subsequent state within its time bound (or unbounded until the trace ends, where an unbounded `always` without counterexample succeeds).
    - `next` requires its subformula to hold in the next captured state index; if the trace ends before a next state is captured, an unsatisfied `next` obligation does not falsely pass when guarded by an active obligation.
    - `eventually` succeeds as soon as its subformula holds in the current or a future state; if the trace ends or the `.within` deadline (measured in captured state timestamps in milliseconds or seconds) expires before the subformula holds, it records a violation.
    - Logical operators `and`, `or`, `not`, and `implies` compose formulas with three-valued finite-trace semantics (`True`, `False`, `Pending`), resolving any remaining `Pending` obligations at end-of-trace (`always` resolves to `True`, `eventually` resolves to `False`).
    - When `now` returns a nested temporal formula, closures inside that returned formula retain any cell values read during the outer `now` invocation, allowing comparisons between an earlier state's value and future states.
    - Every formula evaluation tracks the cell values read during its step so that a violation report records the failing state index, the property name, the formula path, and the exact extracted cell snapshots involved.
- **Action Generator Tree and Sampling**:
  - In every captured state, all exported generators are evaluated and combined into a weighted tree of branches and action-template leaves.
  - Support generator combinators `map`, `filter`, `flatMap`, and `when` guards (where the guard condition is a boolean, extractor cell, or callback).
  - Support parameter generators for integer and float ranges, regular expressions, email addresses, Unicode strings with length bounds, and explicit character sets.
  - If the combined generator tree for a state contains zero selectable leaves (or total weight 0), abort the run with exit status `1` and an explicit no-actions error.
  - In `--swarm` fuzz mode, derive a per-run random subset of top-level action categories using the run's seed so each short run explores with a distinct action bias.
- **Browser Driver Architecture**:
  - Drive Chromium (or an external debugging target via `--remote-debugger`) over the Chrome DevTools Protocol (CDP) WebSocket interface.
  - Default viewport is `1024x768` with device scale factor `1.0` (`--width`, `--height`, `--device-scale-factor`).
  - Default exploration boundary restricts `http:` and `https:` runs to the initial scheme, host, and port, and restricts `file:` runs to the initial file path (allowing query string changes but forbidding sibling files). Providing one or more `--allow-url <MATCH_PATTERN>` flags (using Chrome extension match pattern syntax) replaces the default boundary.
  - Before initial navigation, apply `--chrome-grant-permissions` (granting local-network permissions by default), `--chrome-virtual-time-policy`, extra request headers (`--header`), and browser cookies (`--cookie`).
  - Automatically accept JavaScript `alert`, `confirm`, `prompt`, and `beforeunload` dialogs via CDP dialog handling. Automatically resume debugger pauses caused by page `debugger` statements. Configure downloads into a run-scoped temporary directory so download links release navigation waiting without hanging, and remove the temporary download directory on normal cleanup.
  - Settle state capture after each action by waiting for queued work across an animation-frame boundary and a rendered frame, while also capturing states around navigation events (full loads, same-document navigations, non-document responses, and back/forward cache restorations), synchronous or asynchronous uncaught exceptions, downloads, WebSocket frames, server-sent events, and settled scroll gestures. Navigation that fails to settle within 30 seconds aborts with operational error status `1`.
  - Default browser element discovery inspects the main document, same-origin iframes, open shadow roots, and assigned slot elements. It collects visible in-viewport links (excluding links that target a new tab/window), enabled buttons, inputs (excluding file inputs and focused nonempty text fields), text areas, labels for enabled controls, and visible elements with interactive ARIA roles.
  - Each click or double-click candidate records an element fingerprint (prioritizing test attributes, `id`, ARIA role, accessible name, `href`, `name`, `placeholder`, `type`, and short text content, falling back to DOM structural path) alongside viewport coordinates so `--reproduce` and `shrink` match elements resiliently across minor layout shifts.
  - Default browser action weights: clicks `100`, focused-field input `100` (text areas `4:1` text vs key group `Backspace`/`Tab`/`Enter`/`Escape`; text inputs `3:1`; email inputs `3:1` email vs key group; number inputs `3:1` 1–5 digits vs key group), scrolling `50` (down by at most half a viewport until bottom, then one scroll to top), navigation `10` (back `10` when prior real history exists, forward `1` when next entry is same-origin, reload `1` suppressed after reload or wait), and one-time wait `1` (suppressed after wait).
  - Support explicit browser actions for double-click, multi-step mouse drag with delay, viewport resize, CSS-selected file-input path assignment, and registered asynchronous custom actions executed in the page context with JSON arguments and extractor cell snapshots.
  - Default browser properties assert: navigation status below `400`, no uncaught synchronous exception, no unhandled promise rejection, and no error-level console log. Provide the optional sliding-window resource growth property helper over JS used/total heap, live DOM nodes, event listeners, and layout objects.
- **Terminal Driver Architecture**:
  - Spawn the target `<PROGRAM> [ARGS...]` attached to a pseudo-terminal (`--columns` default `100`, `--rows` default `40`, `--scrollback-lines-max` default `100`, `--quiescence-timeout-ms` default `5`).
  - Feed child output bytes into an in-memory VT/ANSI terminal emulator. Capture a new state when output stays quiet for `--quiescence-timeout-ms` or when continuous output has been drained for `1000` milliseconds.
  - Expose to terminal extractors: the visible cell grid (dimensions, cell text, wide-character continuation flag, foreground/background/underline colors, underline style, and bold, italic, blink, inverse, strike-through, dim, invisible, and overline flags), rendered row strings, cursor position/visibility/blink/shape/color, scroll offset, retained scrollback grid, child exit code and signal when terminated, and last applied action.
  - Default terminal generator emits text input only, choosing equally between a safe Unicode character set (printable ASCII, extended Latin, Greek, Cyrillic, CJK, Hangul, emoji, and pictographs) and a control set of `Enter` and `Tab` (deliberately omitting `Ctrl+C`, `Ctrl+D`, `Ctrl+Z`, and `Alt+Backspace`). Provide optional generator sets for editing keys, arrows, modified arrows, navigation keys, function keys, bracketed paste, PTY+emulator resize, SGR primary-button mouse clicks, and scrollback viewport top/bottom jumps.
  - Default terminal properties assert that a normally exited process has exit code `0` (signal termination is reported in the run summary without failing the normal-exit property) and that no visible cell contains the Unicode replacement character `U+FFFD`.
  - Detect a hung child when the PTY reports dropped input followed by more than 5 seconds of no output (exiting with status `1`), and ensure any running child process is terminated when the run finishes.
- **Trace Format, Inspection, Replay, and Shrinking**:
  - Store traces in a compact, versioned binary container holding run metadata (driver kind, target, seed, viewport/terminal dimensions, specification identifier), ordered state records (index, timestamp, preceding action with element fingerprint, extracted cell values, console/exception/resource deltas, violations, and embedded PNG screenshot or terminal screen snapshot), and optional JavaScript coverage symbols.
  - `ui-prop-tester trace <TRACE_FILE>` supports `--state <INDEX|START..END>` (including open-ended ranges), `--json` (one JSON object per state), `--screen` and `--color` (ANSI terminal screen rendering), and `--screenshots <DIRECTORY>` (writing index-named PNGs, keeping identical files and refusing conflicting existing files).
  - `ui-prop-tester browser inspect [--port <PORT>] [--no-open] <TRACE_FILE>` starts a local HTTP server (default port `1073`) serving an embedded single-page trace inspector UI with timeline scrubbing, before/after screenshots, action details, extracted cell values, resource metric charts, and violation markers.
  - `shrink` runs `--calibration-runs` (default `3`) to verify the input trace reproduces the target `--property` (auto-selected when the trace violates only one property; required when multiple properties failed), then searches shorter action subsequences (chunk deletion followed by single-action deletion) confirming candidates up to `--confirmation-runs-max` (default `5`) within `--time-limit` and `--parallelism`, and writes the shortest confirmed trace to `--output-path`.
- **Bundled Skill and Roster Integration**:
  - Package the `ui-prop-tester` skill as an own-text bundled skill within the 12 KB entrypoint budget and 160 KB directory budget, accompanied by reference pages (browser testing, terminal testing, and trace/replay/shrink workflows) and an executable launcher script.
  - Register the skill in the repository's own-text skill catalog list, text-only exemption list, copied-files manifest, and skill catalog table.
  - Offer `ui-prop-tester` under `available_skills` on the `qa-engineer` and `frontend-developer` teammates, and update the baseline skill and launch oracles for those two teammates.

## Testing Decisions

- **Test External Behavior at Public Boundaries**: Tests must exercise observable CLI outputs, exit codes (`0`, `1`, `2`), written trace files, `trace --json` / `--screen` / `--screenshots` outputs, and live HTTP/PTY interactions rather than internal data structures. Neither implementation code nor test code may contain comments.
- **Modules to Test**:

## Out of Scope

- Publishing or maintaining npm packages, TypeScript declaration packages on a public registry, Nix packages, Docker images, or standalone GitHub Actions.
- Antithesis guest environment detection or Antithesis proprietary random source integration.
- Inspecting or clicking inside cross-origin iframes (excluded by browser same-origin rules).
- Custom registered action callbacks in terminal mode (custom actions are browser-only).
- Embedding temporary browser download contents into the binary trace file.
- Adding runtime dependencies to `horch-core`, `horch`, or `horch-marketplace`.

## Open Questions

1. **Crate path and binary name**:
   - **Question**: Where should the new Rust crate live in the workspace, and what should the binary be named?
   - **Options**:
     - **Option 1**: Create `crates/ui-prop-tester` as a Cargo workspace member producing a binary named `ui-prop-tester`.
     - **Option 2**: Put the Rust crate inside `skills/ui-prop-tester/engine/` producing `ui-prop-tester`.
     - **Option 3**: Add `ui-prop-tester` as a subcommand of `crates/horch`.
   - **Recommendation**: **Option 1 (`crates/ui-prop-tester`, binary `ui-prop-tester`)**. `crates/horch-core/build.rs` embeds every file under `skills/` into the `horch` binary and enforces a 160 KB per-skill directory budget (`skills_bundled_size_budget`). Placing a Rust crate under `skills/` would embed all its source files into `horch-core` and exceed the 160 KB cap if build artifacts ever land there, whereas a workspace member at `crates/ui-prop-tester` keeps `horch` small and leaves `scripts/check-deps.sh` untouched.

2. **How users and agents get the binary**:
   - **Question**: How should users and fleet workers obtain the `ui-prop-tester` executable (`horch self-update`, `cargo install`, or build on first use)?
   - **Options**:
     - **Option 1 (Build on first use + `cargo install`)**: The skill launcher `skills/ui-prop-tester/scripts/ui-prop-tester` checks `UI_PROP_TESTER_BIN`, then `ui-prop-tester` on `PATH` (from `cargo install --path crates/ui-prop-tester`), then `~/.local/state/horch/ui-prop-tester/bin/ui-prop-tester`. If none is present and a workspace checkout is available, the launcher builds `cargo build --release -p ui-prop-tester` into `~/.local/state/horch/ui-prop-tester/bin/ui-prop-tester` on first use; outside a checkout it exits with status `3` and prints the `cargo install` command.
     - **Option 2 (`horch self-update` and `just install`)**: Add `ui-prop-tester` to `RELEASE_BINARIES` in `crates/horch/src/lib.rs`, `.github/workflows/release.yml`, `just install`, and `horch self-update` so every release archive ships it alongside `horch` and `herdr-install`.
     - **Option 3 (`cargo install` only)**: Require the operator or worker to run `cargo install --path crates/ui-prop-tester` manually before using the skill.
   - **Recommendation**: **Option 1 (Launcher resolves `UI_PROP_TESTER_BIN` -> `PATH` -> cached build-on-first-use in `~/.local/state/horch/ui-prop-tester/bin/ui-prop-tester`)**. Existing tests in `crates/horch/src/lib.rs` (`trf_47_release_assets_hold_only_horch_and_herdr_install` and `trf_47_just_install_builds_only_horch_and_herdr_install`) explicitly lock `RELEASE_BINARIES` to `["horch", "herdr-install"]`. Option 1 respects that contract, mirrors `skills/hark/scripts/hark`, and works automatically for any fleet worker running in the repository as well as any user who runs `cargo install --path crates/ui-prop-tester`.

3. **The property and generator specification language**:
   - **Question**: What language and execution engine should specifications use?
   - **Options**:
     - **Option 1 (JavaScript / TypeScript ES modules via an embedded Rust JS engine plus CDP page evaluation)**: Embed a pure-Rust JS engine (`boa_engine` with a lightweight TypeScript type-stripper) in `crates/ui-prop-tester` to load user ES modules, evaluate temporal formulas (`now`, `always`, `next`, `eventually`, `.within`, `and`, `or`, `not`, `implies`), and sample action generator trees, while evaluating browser DOM extractors and custom browser actions in the live paused Chromium page over CDP `Runtime.evaluate`.
     - **Option 2 (JSON / Rhai DSL)**: Replace JavaScript/TypeScript specifications with a custom Rhai or JSON specification format.
     - **Option 3 (External Node/Deno subprocess)**: Spawn an external `node` subprocess to evaluate specification modules over IPC.
   - **Recommendation**: **Option 1 (JavaScript / TypeScript ES modules via `boa_engine` with TS type stripping and CDP page evaluation for browser DOM callbacks)**. The behavior specification relies heavily on JavaScript/TypeScript closures (for example capturing a cell value in `now((s) => ...)` and comparing it inside a nested `next` or `eventually` callback) and browser DOM APIs (`document`, `window`). Option 1 preserves full behavioral compatibility for both browser and terminal specifications in a single self-contained Rust binary with no external Node runtime requirement.

4. **The browser driver approach**:
   - **Question**: How should `ui-prop-tester` launch and control Chromium?
   - **Options**:
     - **Option 1 (Direct CDP WebSocket client and browser process manager)**: Manage the local Chromium/Chrome child process (or attach to `--remote-debugger <URL>`) and speak the Chrome DevTools Protocol directly over a WebSocket connection (`tungstenite` + `serde_json`).
     - **Option 2 (High-level Rust browser crate such as `chromiumoxide` or `headless_chrome`)**: Use a third-party wrapper library around CDP.
     - **Option 3 (Playwright / WebDriver subprocess)**: Drive the browser through an external Playwright or WebDriver process.
   - **Recommendation**: **Option 1 (Direct CDP WebSocket client)**. Features required by the behavior spec—`Emulation.setVirtualTimePolicy`, `Profiler.startPreciseCoverage` with branch symbol mapping, `Performance.getMetrics` for sliding-window heap/DOM/listener/layout counters, `Debugger.paused` auto-resumption, `Page.handleJavaScriptDialog`, `Browser.setDownloadBehavior`, and attaching to existing targets without navigation in `test-external`—map directly to raw CDP methods and events that high-level wrapper crates either hide or complicate.

5. **The terminal driver approach**:
   - **Question**: How should `ui-prop-tester` manage the pseudo-terminal and emulate the terminal screen?
   - **Options**:
     - **Option 1 (`libc` Unix PTY + `vt100` / `vte` state machine)**: Allocate the pseudo-terminal with `libc` (`openpty`, `ioctl` `TIOCSWINSZ`, non-blocking reads with `poll`, signal/waitpid lifecycle) and maintain the screen and scrollback grids with a Rust VT parser (`vt100` or `vte`).
     - **Option 2 (`portable-pty` + `alacritty_terminal`)**: Use cross-platform PTY and full terminal emulator crates.
     - **Option 3 (Custom VT parser from scratch)**: Write a custom escape-sequence parser with no terminal crate.
   - **Recommendation**: **Option 1 (`libc` PTY + `vt100` / `vte`-backed grid)**. The fleet host is macOS/Linux Unix where `libc` PTY calls are small, deterministic, and give direct visibility into PTY write buffer backpressure (needed for the dropped-input + 5-second silence hang detector). Pairing `libc` with a focused VT parser supports all required cell attributes (RGB/indexed colors, underline style and color, bold/italic/blink/inverse/strikethrough/dim/invisible/overline, wide characters, cursor state, and scrollback) with minimal dependencies. We also recommend populating the extractor-visible scrollback grid from the retained scrollback lines rather than leaving it empty.

6. **Determinism, seeding, and replay**:
   - **Question**: How should `ui-prop-tester` guarantee deterministic execution and replay?
   - **Options**:
     - **Option 1 (`SplitMix64` with explicit `--seed <u64>` plus fingerprint-based `--reproduce <TRACE_FILE>`)**: Use `SplitMix64` for all random draws (action tree weights, parameter generation, and `--swarm` category subsets), add `--seed <u64>` (and `UI_PROP_TESTER_SEED`) to `test` and `fuzz`, record the seed in every trace header and console summary, and support `--reproduce <TRACE_FILE>` using recorded actions and browser element fingerprints.
     - **Option 2 (Trace replay only, no CLI seed flag)**: Omit `--seed` as in the researched upstream revision and rely only on `--reproduce <TRACE_FILE>` for reproduction.
   - **Recommendation**: **Option 1 (`SplitMix64` with `--seed <u64>` plus `--reproduce <TRACE_FILE>`)**. The operator specifically requested wrapping a "deterministic tool" in the skill, and the behavior research notes the absence of a public seed flag as an upstream gap. Adding `--seed <u64>` makes every random walk and fuzz campaign reproducible from a single integer while keeping full `--reproduce` and `shrink` trace compatibility.

7. **Test seams**:
   - **Question**: Do these seams match your expectations?
   - **Options**:
     - **Option 1**: Test the specification loader, temporal evaluator, action generators, trace CLI, replay, and shrinking through the CLI runner over an in-memory `Driver` fake; test the terminal driver over real local PTY child programs in `cargo test`; and test the 45 browser behaviors against a local in-process HTTP/WebSocket fixture server.
     - **Option 2**: Run all property-engine, replay, and shrinking tests exclusively through a live Chromium process.
   - **Recommendation**: **Option 1**. Separating the `Driver` trait seam lets the core temporal logic, generator sampling, trace formatting, replay, and shrinking run hermetically and deterministically in milliseconds during every `cargo test` gate, while dedicated PTY and local-server browser integration suites verify the real drivers end-to-end.
