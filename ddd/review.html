Do the 178 existing OS-specific sites in production code move behind the new platform layer?

A

Only new fleetd code uses the platform layer; existing sites stay

Pros
  • Smallest change
  • Matches the design's scope for the layer
Cons
  • 2 styles of OS code live side by side
Risks
  • Windows gaps in old code (Unix sockets, unknown machine probe) stay hidden
B

Move the existing sites that fleetd calls behind the layer as each phase touches them

Pros
  • Fleetd paths become first-class on all 3 OSes
  • Work is spread over the phases
Cons
  • Each phase grows
Risks
  • A phase gate covers less than the code it changes
C

Move all 178 sites behind the layer in 1 dedicated phase

Pros
  • 1 consistent rule enforced by arch_scan everywhere
Cons
  • A large change with no failure it fixes directly
Risks
  • Delays the phases that stop daily stalls
Would flip if
  • Windows is not used day to day
  • arch_scan can enforce the rule only on whole crates
  • A phase gate fails because of a moved site

Is fleetd a change to horch or a new system that replaces it?

Achosen

Brownfield: fleetd is a set of changes to horch (keep, change, add)

Pros
  • Reuses the ledger, procid, herdr client, adapters and arch tests
  • Each phase keeps the fleet usable
Cons
  • Old shapes such as the v7 schema constrain the new model
Risks
  • A preserved behavior is dropped by accident
Why

The design says the design is a set of changes to horch, not a rewrite (Where multi-herdr stands today, Keep, change, add), and fleetd is a subcommand of the single horch binary (Amendment D9).

B

Rewrite: a new control plane that replaces horch

Pros
  • A clean model with no legacy shapes
Cons
  • Loses the preserved behaviors and the adapters
Risks
  • Lost work and a stuck fleet during the switch
C

Greenfield beside horch: a separate daemon that horch calls

Pros
  • Independent release
Cons
  • 2 versions of CLI and daemon can differ
Risks
  • Breaks C1: 1 binary, 1 version
Would flip if
  • The operator decides to fork horch into a new product

We wrote down why fleetd exists, who it serves, what counts as success and how big it may get.
decided
fleetd is a change to horch, not a new product. It ships inside the 1 horch binary, for 1 operator and 1 team. Success is 4 numbers: idle tasks caught in under 10 minutes, 0 lost work, 0 tasks outside an approved plan, 0 attempts burned by usage limits.
assumed
The design gives no number for using the subscription fully, so we used a proxy: no usage window resets with usage left while work is ready.
riskiest
If the proxy for full usage is wrong, later steps may build pacing toward the wrong target. The 178 old OS-specific code sites are also still undecided, which affects how first-class Windows really is.
