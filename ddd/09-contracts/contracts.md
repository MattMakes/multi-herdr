# Message contracts — fleetd: the horch fleet control plane

## In plain words

This step wrote 21 contracts: the exact shape of each file or request that crosses a process line in fleetd. These are operator commands, files the sub-orchestrators and workers write, files fleetd writes for them, and facts from git, the agent CLI, the provider and the clock. Each contract has a schema, a good example and bad examples it must reject.

**Decided:** The 21 messages that stay inside the 1 horch binary get no contract, only code tests. result.json and plan.yaml keep the field names of the design examples.

**Assumed:** The other files keep the connect names (taskId, ideaId) for now. The operator decides the single naming style at the review (decision D1).

**Riskiest:** task.yaml, heartbeat.json and verdict.json have no contract, because connect lists no message for them (Q1). A worker or the wrapper built from this catalogue alone would miss them.

fleetd asks the operator to approve an idea's assumptions; until the operator approves or revises, the idea's lease is paused.

|---|---|---|---|

Example:


#### Add Idea (`add-idea`) — command v1.0, Draft

The operator captures an idea from any terminal; fleetd records it as captured, and the dispatcher starts its sub-orchestrator on the next pass.

- sent by client operator → ideas · open-host-service · sync via other, also via file (at-least-once, async): request file under the state root when fleetd is down; fleetd reads it at start
- owners: core-team · reviewers: core-team · client: operator · glossary: ddd/glossary.md#ideas-context
- schema: `ddd/09-contracts/schemas/add-idea.schema.json` · example: `ddd/09-contracts/examples/add-idea.json`

Payload (JSON Schema 2020-12, closed (`additionalProperties: false`)):

| Field | Type | Required | Description |
|---|---|---|---|
| text | string | yes | The idea text, or the content of the file given with horch idea add -f. |
| featureId | string | no | Optional. The feature the idea joins (horch idea add --to). Absent: the idea starts a new feature. |

Example:

```json
{
  "text": "Retry sync with backoff and log each retry"
}
```

Semantics:

- Each accepted request creates exactly 1 immutable idea.md and 1 ledger row in state captured, and the reply carries its new ideaId.
- No idempotency key exists: a request file that is ingested twice creates 2 ideas (open question Q2).
- Only fleetd writes the ledger. When fleetd is down, horch writes a request file and fleetd reads it at start, so the reply arrives only on the sync channel.

Terms of use: Additive changes only within version 1.x; a removed, renamed or retyped field is 2.0. The horch CLI and fleetd ship in 1 binary, so the operator never meets a version skew, but a request file written by an older horch and read at start must still validate.

| reason | string | yes | Why the task escalated. Known reasons: attempts and the replan are exhausted, the plan was refused, a rescue failed, a judge CRITICAL item is left after 2 fix rounds, a profile defect (waiting_approval). Open string. |

Example:

```json
{
  "taskId": "T-0007-03",
  "reason": "attempts exhausted after 1 replan: the verifier rejected 3 attempts"
}
```

Semantics:

- The reconcile pass is level-triggered, so the reaction can run again: 1 needs-you/ file per (taskId, reason), and integration records it once per taskId.
- Nothing is removed on escalation: the worktree and branch stay, and only the operator abandons the branch.
- An operator requeue of the task resets its attempt count (attempt_floor, 04 L8).

Terms of use: Additive changes only within version 1.x; a removed, renamed or retyped field is 2.0. The horch CLI and fleetd ship in 1 binary, so the operator never meets a version skew, but a request file written by an older horch and read at start must still validate.

### Accepts from clients

#### Write Result (`write-result`) — command v1.0, Draft

The worker claims its attempt is finished; the claim licenses fleetd to run the verifier, and only the verifier moves the task to done.

- sent by client worker → task-execution · open-host-service · at-least-once via file
- owners: core-team · reviewers: core-team · client: worker · glossary: ddd/glossary.md#task-execution-context
- schema: `ddd/09-contracts/schemas/write-result.schema.json` · example: `ddd/09-contracts/examples/write-result.json`

Payload (JSON Schema 2020-12, closed (`additionalProperties: false`)):

| Field | Type | Required | Description |
|---|---|---|---|
| task | string | yes | The task of the attempt. |
| attempt | string | yes | The attempt directory name, e.g. A1. |
| status | string | yes | The worker's claim. Known value in the design: completed. Open string: the design gives no closed list (open question Q3). |
| summary | string | yes | What the worker did, in 1 or 2 sentences. |
| commits | array of string | yes | Commit ids on the task branch, short or full hex. May be empty. |
| files_changed | array of string | no | Repository paths the attempt changed. |
| acceptance_self_check | array of object | no | The worker's own run of the acceptance commands. Advisory: the verifier runs them again. |
| acceptance_self_check[].run | string | yes |  |
| acceptance_self_check[].exit | integer | yes | Exit code the worker saw. |
| notes_for_next | string | no | Notes for the next task or attempt. |

Example:

```json
{
  "task": "T-0007-02",
  "attempt": "A1",
  "status": "completed",
  "summary": "Added retry logging in SyncClient._retry with attempt and delay.",
  "commits": [
    "3f9c2ab"
  ],
  "files_changed": [
    "src/sync/client.py",
    "tests/test_backoff.py"
  ],
  "acceptance_self_check": [
    {
      "run": "pytest tests/test_backoff.py -q -k logs",
      "exit": 0
    }
  ],
  "notes_for_next": "Delay is logged in ms."
}
```

Semantics:

- 1 result per attempt: result.json is written atomically and never rewritten; fleetd ingests it once per (task, attempt).
- The result is a claim, not a fact: a task is done only when result.json validates and the verifier's check passes in the worker sandbox (RR-3, SR-4).
- acceptance_self_check is advisory; the verifier never trusts it.
- A process that exits with commits and no result gets 1 short resume of the same session to write it; an exit without a valid result is outcome no_result.

Terms of use: Additive changes only within version 1.x; a removed, renamed or retyped field is 2.0. fleetd rejects a file or request that fails this schema (design protocol rule 4), so a 2.0 ships together with the matching horch, fleet helper and prompt changes.
