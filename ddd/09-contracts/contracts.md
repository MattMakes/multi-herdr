# Message contracts — fleetd: the horch fleet control plane

## In plain words

This step wrote 30 contracts: the exact shape of each file or request that crosses a process line in fleetd. These are operator commands, files the sub-orchestrators, workers and the wrapper write, files fleetd writes for them, and facts from git, GitHub, herdr, the agent CLI, the provider and the clock. Each contract has a schema, a good example and bad examples it must reject.

**Decided:** Every field name is snake_case, as in the design (D1, option B). Each operator command carries an idempotency_key and gets back accepted, or refused with a reason. result.json status is completed, blocked or failed. reset_at is optional.

**Assumed:** The idempotency_key is an opaque string of 1 to 128 characters, because no source gives its format. verdict.json decision is done or ready, from the Verifier row of the design.

**Riskiest:** heartbeat-written and task-escalated sit inside 1 deployable, so the checker warns about them. If the wrapper later runs in fleetd itself, heartbeat-written stops being a wire contract.

#### Approval Requested (`approval-requested`) — event v1.0, Draft

fleetd asks the operator to approve an idea's assumptions; until the operator approves or revises, the idea's lease is paused.

- ideas → client operator · open-host-service · at-least-once via file
- owners: core-team · reviewers: core-team · client: operator · glossary: ddd/glossary.md#ideas-context
- schema: `ddd/09-contracts/schemas/approval-requested.schema.json` · example: `ddd/09-contracts/examples/approval-requested.json`

Payload (JSON Schema 2020-12, closed (`additionalProperties: false`)):

| Field | Type | Required | Description |
|---|---|---|---|
| idea_id | string | yes | The idea in awaiting_approval. |
| assumptions_hash | string | yes | sha256 of the assumptions.md to approve; horch idea approve sends it back. |

Example:

```json
{
  "idea_id": "I-0012",
  "assumptions_hash": "9f2c4e1a7b3d5f60812a4c6e8b0d2f4a6c8e0b2d4f6a8c0e2b4d6f8a0c2e4b6d"
}
```

Semantics:

- 1 needs-you/ file per (idea_id, assumptions_hash), plus a herdr notification; a revised assumptions.md gets a new file.
- Waiting is not a stall: 1 reminder an hour during working hours, and after 7 days with no answer the idea goes to parked with a note in needs-you/.

Terms of use: Additive changes only within version 1.x; a removed, renamed or retyped field is 2.0. The horch CLI and fleetd ship in 1 binary, so the operator never meets a version skew, but a request file written by an older horch and read at start must still validate.

### Accepts from clients

#### Add Idea (`add-idea`) — command v1.0, Draft

The operator captures an idea from any terminal; fleetd records it as captured, and the dispatcher starts its sub-orchestrator on the next pass.

- sent by client operator → ideas · open-host-service · sync via other, also via file (at-least-once, async): request file under the state root when fleetd is down; fleetd reads it at start
- owners: core-team · reviewers: core-team · client: operator · glossary: ddd/glossary.md#ideas-context
- schema: `ddd/09-contracts/schemas/add-idea.schema.json` · example: `ddd/09-contracts/examples/add-idea.json`

Payload (JSON Schema 2020-12, closed (`additionalProperties: false`)):

| Field | Type | Required | Description |
|---|---|---|---|
| text | string | yes | The idea text, or the content of the file given with horch idea add -f. |
| feature_id | string | no | Optional. The feature the idea joins (horch idea add --to). Absent: the idea starts a new feature. |
| idempotency_key | string | yes | Opaque key that the horch CLI makes once per command run. The command channel request and the request file of the same run carry the same key. fleetd applies a request once per key and returns the first outcome again (orchestrator, D15). |

Example:

```json
{
  "text": "Retry sync with backoff and log each retry",
  "idempotency_key": "add-idea-7f3a9c2e"
}
```

Semantics:

- Each accepted request creates exactly 1 immutable idea.md and 1 ledger row in state captured, and the reply carries its new idea_id.
- Only fleetd writes the ledger. When fleetd is down, horch writes a request file and fleetd reads it at start, so the reply arrives only on the sync channel.
- fleetd applies a request once per idempotency_key and returns the first outcome again; the request file of the same command run carries the same key (orchestrator, D15).
- A refused request returns outcome refused with its reason (orchestrator, D15).

Terms of use: Additive changes only within version 1.x; a removed, renamed or retyped field is 2.0. The horch CLI and fleetd ship in 1 binary, so the operator never meets a version skew, but a request file written by an older horch and read at start must still validate.

  "feature_id": "F-0003",
  "pr_url": "https://github.com/MattMakes/multi-herdr/pull/349"

### Calls out to external systems

#### Open Pull Request (`open-pull-request`) — command v1.0, Draft

integration opens the pull request of a ready feature after its full gate passes: pr gh calls GitHub, pr manual pushes the feature branch and records the compare URL. A stacked feature uses the lower feature branch as base.

_Inherited contract: github owns the wire format (anticorruption-layer); this schema is our view of the message at the ACL boundary — what we send._

- called by integration → github · anticorruption-layer · sync via other
- owners: github · reviewers: core-team · glossary: ddd/glossary.md#landing-and-integration-context
- schema: `ddd/09-contracts/schemas/open-pull-request.schema.json` · example: `ddd/09-contracts/examples/open-pull-request.json`

Payload (JSON Schema 2020-12, closed (`additionalProperties: false`)):

| Field | Type | Required | Description |
|---|---|---|---|
| feature_id | string | yes | The ready feature. |
| branch | string | yes | The feature branch. |
| base_branch | string | yes | The primary branch, or the lower feature branch for a stacked feature. |

Example:

```json
{
  "feature_id": "F-0003",
  "branch": "retry-logging",
  "base_branch": "main"
}
```

Semantics:

- 1 pull request per feature_id; integration reads features.pr first and does not open a second one.
- A retry after a timeout reads features.pr and GitHub first, so it opens no second pull request.
- Every git network call has a wall-clock bound (push 10 min) and never retries (04 F11).

Terms of use: GitHub owns the wire contract. The schema is our view at the github adapter of integration; a GitHub change lands in that adapter only. Additive changes only within version 1.x.

### Accepts from clients

#### Abandon Task Branch (`abandon-task-branch`) — command v1.0, Draft

The operator abandons an escalated task branch; its work survives on a rescue ref, and the branch leaves the landing queue for good.

- sent by client operator → integration · open-host-service · sync via other, also via file (at-least-once, async): request file under the state root when fleetd is down; fleetd reads it at start
- owners: core-team · reviewers: core-team · client: operator · glossary: ddd/glossary.md#landing-and-integration-context
- schema: `ddd/09-contracts/schemas/abandon-task-branch.schema.json` · example: `ddd/09-contracts/examples/abandon-task-branch.json`

Payload (JSON Schema 2020-12, closed (`additionalProperties: false`)):

| Field | Type | Required | Description |
|---|---|---|---|
| branch | string | yes | The task branch, ledger branches.name, e.g. fleet/I-0007/T-0007-03. |
| task_id | string | yes | The escalated task that owns the branch. |
| idempotency_key | string | yes | Opaque key that the horch CLI makes once per command run. The command channel request and the request file of the same run carry the same key. fleetd applies a request once per key and returns the first outcome again (orchestrator, D15). |

Example:

```json
{
  "branch": "fleet/I-0007/T-0007-03",
  "task_id": "T-0007-03",
  "idempotency_key": "abandon-task-branch-7f3a9c2e"
}
```

Semantics:

- Only the operator abandons a task branch; abandoned is terminal.
- The branch is dropped only after its rescue ref exists and is verified (I10, CC7); the reply always names that ref.
- An abandoned branch is not abandoned twice: a repeat returns the same rescue_ref and changes nothing.
- fleetd applies a request once per idempotency_key and returns the first outcome again; the request file of the same command run carries the same key (orchestrator, D15).
- A refused request returns outcome refused with its reason (orchestrator, D15).

Terms of use: Additive changes only within version 1.x; a removed, renamed or retyped field is 2.0. The horch CLI and fleetd ship in 1 binary, so the operator never meets a version skew, but a request file written by an older horch and read at start must still validate.

_Inherited contract: git owns the wire format (anticorruption-layer); this schema is our view of the message at the ACL boundary._

- received by integration ← git · anticorruption-layer · sync via other

| Field | Type | Required | Description |
|---|---|---|---|

Terms of use: git owns the wire fact; this schema is our view of it at the ACL boundary. Changes in git land in the integration git adapter; nothing else reads git directly. Additive changes only within version 1.x.
