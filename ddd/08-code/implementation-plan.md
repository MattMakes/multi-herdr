# Implementation plan - fleetd: the horch fleet control plane

Produced by `ddd-code` on 2026-11-12 and revised on 2026-11-16 for amendments A23 to A37, from `ddd/07-define/define.json`, `ddd/04-strategize/strategize.json`, `ddd/05-connect/connect.json`, `ddd/06-organise/organise.json`, `ddd/02-discover/discover.json` and the Migration plan of `docs/specs/fleetd/design.md`. Language rust · framework none · architecture hexagonal · deployables horch · scaffold generated: no

## In plain words

This plan says in which order to build fleetd, in 9 slices. The order is the 9 phases of the design's migration plan (Phase 0, Phase P, Phases 1 to 7), so each slice ships only when its gate tests pass. Each slice uses only the mechanisms of its own phase or of an earlier phase (design: What each gate needs).

**Decided:** All 6 parts of the design become modules under `crates/horch-core/src/fleetd/`. The platform layer is the leaf crate `crates/horch-platform` (root `crates/horch-platform/src/`), which every context calls. worker-profiles owns the fleet-run wrapper and the 1 launcher (D3 option B, SR-7). fleet-runtime owns the job runner: every slow piece of work (a check, a gate, a trial merge, a rebase, a git fetch or push, a worktree add, remove or list, a rescue, docs sync, conformance) runs as a job outside the 5 s pass (A23, A32, A33). Each slice names its failing tests first, then the modules.

**Assumed:** The existing modules (taskledger, vcs, runtime, roster, harness) stay where they are and are wrapped by adapters, until the phase that replaces their behaviour removes the old path. In Phases 1 to 4 the horch commands still write the ledger, through the same `transition()` as fleetd; fleetd is the only writer from Phase 5 (A36).

**Riskiest:** If a slice leaves the old path in place, the old watchdog and fleetd can both act on 1 task. Each slice therefore ends with the removal of the old path it replaces, and Slice 1 stops the old watchdog. Slice P moves 178 OS-specific sites at once; its only safety net is that each test gives the same result before and after the move. The job runner of Slice 1 is new and every later slice depends on it.

---

## Order and why
1. The design's migration plan fixes the order (assumption A8). Phases 1 to 4 stop most daily stalls and stop lost worktrees, so they come first. Slice P comes right after Slice 0 (operator decision D16): it builds the platform crate that every later slice calls. This puts fleet-runtime (the pass, the job runner, the fleet clock, the launcher) before the core contexts, because every core rule runs inside its reconcile pass and every slow step is a job.
2. `task-execution` is the first core context, in slices 1, 2 and 4. Its pivotal event `task-done` arrives in slice 4, when the verifier replaces the worker's own done.
3. `integration` lands 1 feature per run in slice 4 (the tables `features`, `branches`, `bundles`, `bundle_members`, `gate_runs` and `remote_tips`, the landing and the bundle state machines). Several features, stacks and trial merges come in slice 6 with `ideas`, because a plan must land through the single writer to be all-or-nothing (design: Phase 6 depends on Phase 5). Until slice 6, a run stands for its idea and its feature.
4. Read models are the existing horch CLI views, rebuilt from the ledger in the slice that changes their tables.
5. Each slice has the test of its phase in "What a release does to a run in flight" of the design: a run that starts on the earlier phase is updated and goes on.

Each slice is a vertical slice: the tests in "Tests (write first)" are written and seen to fail before the modules, as define N3 requires for the quality attributes of priority high. Each slice is done when its tests pass, its gate rows are off the list of expected failures, and the fitness tests still pass.
